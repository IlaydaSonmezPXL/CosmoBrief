## 1. Project Overview

Cosmo Brief is a three-tier web application that serves as a personal space news companion. It consumes real articles from the Spaceflight News API (SNAPI v4) and enriches them through a stateful interaction model. Articles move through a defined lifecycle. Simplified explanations of articles are generated by OpenAI GPT-4o-mini, persisted permanently, versioned, and rated by the user. The system accumulates a per-user reading history that builds into a meaningful map of explored topics. An admin role provides system-wide usage statistics.

**Infrastructure summary:**

| Tier | Role | VM Address | Port |
|---|---|---|---|
| Frontend | React static site, served by nginx | 10.10.0.10 | 8080 (Vagrant) / 80 (AWS) |
| Backend | FastAPI API, all business logic, AI calls | 10.10.0.20 | 8000 |
| Storage | PostgreSQL 16 | 10.10.0.30 | 5432 |

All three machines run AlmaLinux 9, provisioned via Vagrant (local) or EC2 (AWS extra), deployed via a single Ansible command.

**Single deployment command (from repo root):**
```bash
ansible-playbook -i local-deploy/inventory.ini ansible/playbook.yml --vault-password-file .vault_pass
```

## 2. Functional Requirements — Frontend Tier

### 2.1 Article Feed

- FR-FE-01: The frontend must display a paginated or scroll-based feed of space news articles fetched from the backend API. It must never call SNAPI directly.
- FR-FE-02: Each article card must display: title, news source (`news_site`), publication date, summary, thumbnail image (`image_url` if available), freshness label (Fresh / Aging / Archived), and current state badge.
- FR-FE-03: The feed must visually distinguish articles by state. Dismissed articles are hidden from the default feed and accessible only via explicit filter.
- FR-FE-04: The feed must support filtering by state (All, Saved, Explained, Dismissed) and by freshness (Fresh, Aging, Archived).

### 2.2 Article Detail View

- FR-FE-05: Clicking an article opens a detail view. This triggers a `GET /articles/:id` call which causes the backend to transition the article from `new` → `read` as a side effect.
- FR-FE-06: The detail view must display: full title, source, publication date, link to original article, freshness label, current state, and the status of all four explanation modes.
- FR-FE-07: ~~Save and Dismiss action buttons removed.~~ The detail view shows only the AI explanation modes. State advances automatically (new→read→explained).

### 2.3 Explanation Interaction

- FR-FE-08: The detail view displays four mode buttons: "Explain like I'm 12", "Explain like a caveman", "Explain like an alien", "Explain like a story". Each button shows whether an explanation is available, needs regeneration, or has not been requested.
- FR-FE-09: Requesting an explanation calls `POST /articles/:id/explanations`. The frontend shows a loading indicator while awaiting the response.
- FR-FE-10: The returned explanation text renders in a clearly designated section. The version number and timestamp are shown.
- FR-FE-11: After an explanation is displayed, thumbs-up and thumbs-down rating controls appear. After rating is submitted, the controls update to show the recorded rating and become inactive for the current version.
- FR-FE-12: A "Version history" control allows the user to view all previous versions of an explanation for a given article + mode, with timestamps.

### 2.4 User Reading Map

- FR-FE-13: A dedicated Reading Map view displays all topic tags accumulated by the current user, grouped by tag with an article count per tag (e.g. "Mars — 4 articles").

### 2.5 Authentication

- FR-FE-14: The application has a login page and a registration page. All article interaction and explanation features require authentication.
- FR-FE-15: On successful login, the JWT access token is stored in `localStorage` and attached to all subsequent API requests via the `Authorization: Bearer <token>` header.
- FR-FE-16: A logout action clears the token from `localStorage` and redirects to the login page. No server-side token invalidation is required.
- FR-FE-17: On receiving a 401 response from the backend, the Axios interceptor automatically clears the token and redirects to `/login`.

### 2.6 Admin Dashboard

- FR-FE-18: Users with the `admin` role see an Admin Dashboard link in the navigation. Regular users do not see this link. The backend enforces the restriction regardless of frontend visibility.
- FR-FE-19: The Admin Dashboard displays: total registered users, total explanations generated, breakdown of generations by mode, total OpenAI prompt and completion tokens consumed, top 10 topic tags across all users, and total thumbs-up vs thumbs-down ratings.

### 2.7 Health Endpoint

- FR-FE-20: The nginx server must expose `GET /health` returning HTTP 200 with a non-empty plaintext or JSON response body (e.g. `{"status": "ok", "service": "frontend"}`).

## 3. Functional Requirements — Backend Tier

### 3.1 Article Feed Assembly

- FR-BE-01: `GET /articles` fetches articles from SNAPI v4 (`https://api.spaceflightnewsapi.net/v4/articles/`), applies freshness classification, merges per-user article states, and returns the result.
- FR-BE-02: Freshness classification is applied to every article based on `published_at`:
  - `fresh`: published within 48 hours of current UTC time
  - `aging`: published between 48 and 96 hours ago
  - `archived`: published more than 96 hours ago
- FR-BE-03: Articles are cached in the `article_cache` table. If the cache is older than 15 minutes, the backend refreshes from SNAPI on the next request. The TTL is configurable via an environment variable.
- FR-BE-04: Per-user article state is merged into each article response. If no `article_state` record exists for (user_id, article_id), the state is `new`. A database record is created only on first interaction.

### 3.2 State Machine Enforcement

- FR-BE-05: All state transitions are validated by `services/state_machine.py`. Invalid transitions return HTTP 409. The transition table in that module is the single authoritative source.
- FR-BE-06: `GET /articles/:id` triggers an automatic `new → read` transition as a side effect if the article is in the `new` (implicit) state. This does not require a separate API call from the frontend.
- FR-BE-07: The `explained` state is never set by a direct user request. It is set automatically by the backend after the first successful explanation generation for that user + article.

### 3.3 Explanation Generation

- FR-BE-08: On `POST /articles/:id/explanations`, the backend executes the following decision flow:
  1. Look up the most recent explanation record for (user_id, article_id, mode).
  2. If none exists → generate new (version 1).
  3. If exists and `needs_regeneration = false` → return the cached record (HTTP 200, `"source": "cached"`).
  4. If exists and `needs_regeneration = true` → generate new, increment version (HTTP 201, `"source": "generated"`).
- FR-BE-09: Generation calls OpenAI GPT-4o-mini with a structured output schema requesting both the explanation text and a topic tag in a single API call. Both fields are stored.
- FR-BE-10: After generation, the backend stores: explanation text, topic tag, version number, timestamp, prompt tokens used, completion tokens used (from the OpenAI response's `usage` field).
- FR-BE-11: After any generation, the backend always sets the article state to `explained` for that user.
- FR-BE-12: A topic tag record is created for (user_id, article_id) if one does not already exist. Subsequent explanation requests for the same article do not overwrite or duplicate the topic tag.

### 3.4 Rating

- FR-BE-13: `POST /articles/:id/explanations/:mode/:version/rating` accepts `up` or `down`.
- FR-BE-14: Only the most recent version for a given (user_id, article_id, mode) may be rated. Attempting to rate a non-latest version returns HTTP 403.
- FR-BE-15: A version may only be rated once. A second rating attempt returns HTTP 409.
- FR-BE-16: A `down` rating sets `needs_regeneration = true` on that version record.

### 3.5 Authentication and Authorization

- FR-BE-17: `POST /auth/register` creates a new user with role `user`. Passwords are hashed with bcrypt (passlib). Returns HTTP 201 with a JWT access token.
- FR-BE-18: `POST /auth/login` verifies credentials against the database. On success, returns HTTP 200 with a JWT access token. On failure, returns HTTP 401.
- FR-BE-19: All endpoints except `/auth/register`, `/auth/login`, and `/health` require a valid JWT in the `Authorization: Bearer` header. Invalid or missing tokens return HTTP 401.
- FR-BE-20: `GET /admin/stats` requires the requesting user to have `role = 'admin'`. Non-admin authenticated users receive HTTP 403.

### 3.6 Health Endpoint

- FR-BE-21: `GET /health` returns HTTP 200 with a JSON body containing at minimum `status`, `db_status`, and `timestamp`. The `db_status` field is populated by executing a real database query (`SELECT 1`) and reporting the result. An empty 200 is not acceptable.

## 4. Functional Requirements — Storage Tier

### 4.1 Persistent Storage

- FR-ST-01: PostgreSQL 16 installed from the official PGDG repository for AlmaLinux 9 (EL9). No system-default PostgreSQL version is used.
- FR-ST-02: A dedicated application database and a dedicated application user (not the postgres superuser) are created by the Ansible storage role.
- FR-ST-03: Schema is managed entirely by Alembic migrations. The Ansible backend role runs `alembic upgrade head` on every deploy. This is idempotent when no new migrations exist.

### 4.2 Data Durability

- FR-ST-04: PostgreSQL data directory (`/var/lib/pgsql/16/data/`) is never removed, recreated, or reinitialised on a redeploy. The Ansible task that runs `initdb` is conditioned on the data directory not existing (`creates: /var/lib/pgsql/16/data/PG_VERSION`).
- FR-ST-05: Alembic `downgrade` is never called by any Ansible task. Only `upgrade head` is called.
- FR-ST-06: All `alembic/versions/` migration files are permanent. They are never deleted or retroactively modified.

### 4.3 Admin User Seeding

- FR-ST-07: The Ansible storage role seeds the admin user by executing an `INSERT ... ON CONFLICT DO NOTHING` query via `community.postgresql.postgresql_query`. The password hash is a pre-computed bcrypt hash stored in Ansible Vault (`vault_admin_password_hash`). This task runs on every deploy but produces no change if the admin already exists.

### 4.4 Health Verification

- FR-ST-08: Storage health is demonstrated through the backend's `GET /health` endpoint, which includes `db_status` populated by a live `SELECT 1` query against PostgreSQL. This provides observable evidence of real storage interaction.

## 5. Article State Machine

### 5.1 States

| State | Description |
|---|---|
| `new` | Implicit default. No `article_state` DB record exists for this user + article. |
| `read` | User has opened the article detail view. A DB record exists. |
| `explained` | At least one AI explanation exists for this user + article. Set by backend automatically. |

### 5.2 Valid Transitions

| From | To | Trigger | Backend enforced? |
|---|---|---|---|
| `new` (implicit) | `read` | User opens article detail view (`GET /articles/:id`) | Yes — side effect |
| `read` | `explained` | Backend generates first explanation | Yes — automatic, not user-triggered |

### 5.3 Explicitly Invalid Transitions (return HTTP 409)

- `new → explained` (never user-triggered)
- Any backwards transition (e.g. `explained → read`)

### 5.4 Transition Rules

- Rule STM-01: The `services/state_machine.py` module is the single source of truth. It exposes a function `validate_transition(from_state, to_state) -> bool` used by all routers.
- Rule STM-02: The implicit `new` state is represented as `None` (no DB record). `validate_transition(None, 'read')` must return `True`.
- Rule STM-03: State transition records include a `updated_at` timestamp. History of all transitions is not stored — only the current state is persisted.

## 6. Explanation System

### 6.1 Modes

| Mode Key | Display Label |
|---|---|
| `eli12` | Explain like I'm 12 |
| `caveman` | Explain like a caveman |
| `alien` | Explain like an alien |
| `story` | Explain like a story |

Mode keys are stored in the database and used in API paths. Display labels are frontend-only.

### 6.2 OpenAI Call Specification

**Model:** `gpt-4o-mini`

**System prompt (template — mode is injected):**
```
You are a helpful assistant that explains space news articles.
Explain the following article {mode_instruction}.
Also identify a single short topic tag for this article (e.g. "Mars", "Artemis", "Black Holes", "SpaceX", "James Webb").
Respond only in JSON with the following structure: {"explanation": "...", "topic_tag": "..."}
```

**Mode instructions by key:**
- `eli12`: "as if explaining to a 12-year-old, using simple words and relatable comparisons"
- `caveman`: "using only very simple words, short sentences, and primitive concepts as if speaking to a caveman"
- `alien`: "as an alien visitor reporting this human space news back to your home planet. Use alien exclamations like 'Glorp!' and 'Zlorp!' naturally throughout. Express bewildered curiosity about human concepts, occasionally misunderstand Earth things in funny ways, and pepper the explanation with alien slang (glorp, zlorp, florpnax, bleeble, snorkvax). Write as if humans discovering space is both adorable and slightly baffling to your ancient civilization."
- `story`: "as a short compelling narrative story, with a beginning, middle, and end"

**Token tracking:** The `usage` field of every OpenAI API response contains `prompt_tokens` and `completion_tokens`. Both are stored in the `explanations` table.

### 6.3 Generation Decision Flow

```
Request: (user_id, article_id, mode)
    │
    ├─ Query latest explanation record for (user_id, article_id, mode)
    │
    ├─ No record found?
    │       └─ Generate (version = 1)
    │
    ├─ Record found, needs_regeneration = false?
    │       └─ Return cached record (HTTP 200, source = "cached")
    │
    └─ Record found, needs_regeneration = true?
            └─ Generate (version = prev_version + 1)

After generation:
    ├─ Store new explanation record
    ├─ Set article state to "explained" (if not already saved/dismissed)
    └─ Create topic_tag record for (user_id, article_id) if not exists
```

### 6.4 Versioning Rules

- Every generation produces a new record. No existing record is ever modified except for `rating` and `needs_regeneration` fields.
- Version numbers are scoped to (user_id, article_id, mode). They start at 1 and are always integers.
- The full version history is retrievable via `GET /articles/:id/explanations/:mode/history`.

### 6.5 Rating Rules

- Only the most recent version of a (user_id, article_id, mode) combination may be rated.
- Each version may be rated exactly once. The rating is final — no changes are allowed after submission.
- `down` → sets `needs_regeneration = true`.
- `up` → records the positive rating. No effect on generation behaviour.

### 6.6 Topic Tag Rules

- One topic tag record per (user_id, article_id). Created on first explanation generation for that article, regardless of mode.
- Subsequent explanation generations for the same article do not modify the existing topic tag.
- Topic tags power the Reading Map aggregation query: `SELECT tag, COUNT(DISTINCT article_id) FROM topic_tags WHERE user_id = $1 GROUP BY tag ORDER BY count DESC`.

## 9. Non-Functional Requirements

### 9.1 Infrastructure

- NFR-INF-01: Strict 3-tier separation. Frontend, backend, and storage run on separate VMs. No colocation.
- NFR-INF-02: AlmaLinux 9 (AlmaLinux generic/alma9 Vagrant box, pinned to `4.3.12`).
- NFR-INF-03: Full deployment from a single Ansible command after `vagrant up`. No manual steps.

### 9.2 Idempotency

- NFR-IDP-01: Running the playbook a second time against a deployed system produces zero changed tasks and zero restarts.
- NFR-IDP-02: Services that have not changed must not restart. Use `notify`/`handlers` correctly — only tasks that actually produce a change notify the handler.
- NFR-IDP-03: `command` and `shell` modules must not be used. Any exception requires documentation in PROJECT_README.md.
- NFR-IDP-04: All DB initialisation tasks (`initdb`, `createdb`, `createuser`) are guarded by `creates:` or equivalent. They execute only when the target does not yet exist.
- NFR-IDP-05: `alembic upgrade head` runs unconditionally on every deploy. Alembic's internal version tracking ensures it is a no-op when no new migrations exist.

### 9.3 Ansible Structure

- NFR-ANS-01: Three roles: `frontend`, `backend`, `storage`. One play per role targeting its inventory group.
- NFR-ANS-02: All configuration files use Jinja2 templates. No static files with hardcoded values.
- NFR-ANS-03: No hardcoded IP addresses in playbooks or templates. Use `{{ hostvars['backend']['ansible_host'] }}` pattern.
- NFR-ANS-04: Tier-wide settings in `group_vars/{group}.yml`. Host-specific settings in `host_vars/`. No duplicates.
- NFR-ANS-05: Each tier independently redeployable: `--limit frontend`, `--limit backend`, `--limit storage`.
- NFR-ANS-06: `ansible/vault.yml` contains all secrets, encrypted with Ansible Vault.
- NFR-ANS-07: Frontend build uses `delegate_to: localhost` tasks: (1) template `.env.production` locally, (2) run `npm ci && npm run build` locally, (3) copy `frontend/dist/` to VM with `synchronize` or `copy`.

### 9.4 Secrets Management

- NFR-SEC-01: No plaintext secret in any committed file. The encrypted `ansible/vault.yml` is the only location for secret values.
- NFR-SEC-02: `.vault_pass` is git-ignored. Never committed.
- NFR-SEC-03: Backend receives secrets via environment variables rendered from Jinja2 templates by Ansible. No `.env` file is manually maintained.

### 9.5 Health Checks

- NFR-HLT-01: **Frontend:** `GET /health` on port 8080 (Vagrant) returns HTTP 200 with non-empty body.
- NFR-HLT-02: **Backend:** `GET /health` on port 8000 returns HTTP 200 with JSON body including `status` and `db_status` from a live DB query.
- NFR-HLT-03: **Storage:** Demonstrated via the backend health endpoint's `db_status` field, which reflects the result of a real `SELECT 1` query against PostgreSQL.

### 9.6 Data Durability

- NFR-DUR-01: PostgreSQL data directory is never removed or reinitialised by any task that runs on every deploy.
- NFR-DUR-02: Alembic `downgrade` is never called. Schema changes are additive only.
- NFR-DUR-03: The demo must show that data entered before a redeploy is present and accessible after the redeploy.

### 9.7 Backend Service Configuration

- NFR-SVC-01: Backend runs as `gunicorn` with `uvicorn.workers.UvicornWorker`, managed by `systemd`.
- NFR-SVC-02: Number of gunicorn workers: `(CPU_CORES * 2) + 1`. Configurable via `gunicorn_workers` Ansible variable.
- NFR-SVC-03: gunicorn binds to `0.0.0.0:8000` so the frontend VM can reach the backend VM over the private network. The frontend nginx proxies `/api/` to `http://10.10.0.20:8000`.
- NFR-SVC-04: Backend runs as a dedicated non-root system user (`cosmobrief`).
- NFR-SVC-05: Application code lives in `/opt/cosmobrief/` on the backend VM. The Python virtualenv lives at `/opt/cosmobrief/venv/`.

## 10. Extras Specification

All extras are implemented after the core application is complete and passing all graded requirements.

### EXTRA1 — Token-Based Authentication (1 point)

Already integrated as a core feature of Cosmo Brief (see Sections 2.5, 3.5, 7.2). Acceptance conditions:
- JWT issued only after successful login.
- Token stored client-side (localStorage). No server-side blacklisting required.
- All article and explanation routes protected by token validation.
- Unauthorized requests to protected routes return HTTP 401.
- Logout removes the token client-side.

### EXTRA2 — Role-Based Authorization (1 point)

Two roles: `user` and `admin`. Acceptance conditions:
- Roles stored in `users.role` column (application DB).
- `GET /admin/stats` is accessible only to `admin` role. Non-admin authenticated users receive HTTP 403.
- The admin user is seeded by Ansible on first deploy.
- Frontend hides admin navigation for non-admin users, but the backend endpoint enforces the restriction independently.
- Demo shows: regular user receives 403 on `GET /admin/stats`; admin user receives 200.

### EXTRA3 — Central Logging (1 point)

- rsyslog is used as the logging technology. It runs on the **storage VM** (10.10.0.30) as the central log receiver, since it already hosts the only always-on service.
- All three VMs forward application and service logs to the storage VM via rsyslog over UDP/TCP port 514.
- Log entries are identifiable by source hostname (frontend, backend, storage).
- The central logging setup is part of the Ansible deployment (all three roles configure rsyslog).
- Demo shows: perform an action on the frontend; the resulting log entry appears in the central log on the storage VM.

### EXTRA4 — AWS Academy Deployment (3 points)

- Same Ansible roles and `ansible/playbook.yml` used for both Vagrant and AWS.
- Separate inventory file generated by the provisioning script (git-ignored).
- Frontend VM: public subnet with public IP. Backend and storage: private subnet, no public IP.
- Backend and storage accessible by Ansible only via ProxyJump through the frontend VM.
- `group_vars/frontend.yml` sets `frontend_http_port: 80` for AWS inventory; `8080` for Vagrant.
- No hardcoded AWS IP addresses, hostnames, or generated credentials in any committed file.
- Teardown via the provided `provisioning/teardown_pe2_nat_bastion.sh`.
